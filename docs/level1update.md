# 규칙 기반 한국어 TTS 발음교정 엔진 업데이트 상세 설계서

## 1. 목적

이번 업데이트의 목적은 다음 두 가지다.

1. 문맥 추론 없이도 정확하게 판단할 수 있는 숫자·단위 표현을 규칙 기반 엔진에서 최대한 처리한다.
2. 의미가 둘 이상으로 해석될 수 있는 표현은 기존의 일반 숫자 규칙이 임의로 확정하지 않도록 차단하고, 숫자 표면을 그대로 유지하여 통합 LLM이 문장 전체를 보고 처리하게 한다.

이번 단계에서는 서비스로 반환되는 문자열에 다음 정보를 절대 추가하지 않는다.

- 태그
- 마커
- 규칙 이름
- 유보 상태
- 후보 발음
- 디버깅 정보
- JSON 또는 XML
- LLM 전용 식별자

서비스 출력은 지금과 동일한 일반 문자열이어야 한다.

내부적으로는 규칙 판정과 후보 정보를 생성할 수 있지만, 이는 shadow 검증과 로그 분석에만 사용한다.

# 2. 이번 업데이트의 범위

## 2.1 유지할 영역

현재 안정적으로 처리 중인 다음 영역은 기존 정책과 출력 형식을 유지한다.

- 보호 구간
- URL·이메일·경로·파일명·코드
- 날짜
- 명확한 시각과 기간
- 통화
- 백분율
- 온도
- 전화번호
- 분수
- 범위
- 점수 관계
- 비율
- 명확한 측정 단위
- 관리 사전 항목
- 현재 확정적으로 처리되는 수량 단위
- 기존 한자어·고유어 숫자 생성 방식
- 기존 단위 앞뒤의 공백 정책
- 기존 숫자 자릿수와 임계값 정책

현재 정책의 핵심 원칙인 명시적 owner, 명확한 gate, 전체 소비, 모호한 표면 보존, 비재진입 원칙을 그대로 유지한다. fileciteturn3file1L78-L95

## 2.2 변경할 영역

다음 영역만 보완한다.

- 같은 `(숫자)+(단위)` 표면이 의미에 따라 다른 수사 체계를 사용하는 경우
- 현재 일반 단위 규칙이 너무 일찍 표면을 확정하는 경우
- 짧고 명확한 앞뒤 문맥만으로 의미가 확정되는 경우
- 규칙으로 확정할 수 없는 표현이 일반 숫자 fallback으로 재처리되는 경우
- 향후 LLM 판단을 위한 후보 읽기와 의미 유형의 내부 생성

# 3. 절대적인 출력 호환성 원칙

## 3.1 서비스 출력

규칙 엔진의 외부 출력은 기존과 같은 일반 문자열이어야 한다.

예를 들어 내부적으로 다음과 같이 판단하더라도:

- 표면: `3번`
- 상태: 문맥 판단 유보
- 후보: `세 번`, `삼 번`

서비스 출력은 다음과 같아야 한다.

```text
3번
```

다음처럼 출력해서는 안 된다.

```text
<DEFER>3번</DEFER>
[세 번|삼 번]
3번{occurrence_or_identifier}
```

## 3.2 기존 입력·출력 인터페이스

기존 서비스가 사용하는 규칙 엔진 호출 결과에는 다음 변화가 없어야 한다.

- 반환 자료형
- 인코딩
- 줄바꿈 처리
- 문장 순서
- 보호 토큰 처리
- 오류 반환 방식
- 일반 문자열 형식

내부 판정 정보는 기존 서비스 응답과 물리적으로 분리한다.

## 3.3 출력 모드 분리

운영상 다음 두 개의 동작 모드를 구분해야 한다.

### 기존 호환 모드

- 현재 서비스 결과를 유지한다.
- 새 규칙 판정은 shadow로만 기록한다.
- 유보 판정이 발생하더라도 실제 출력은 기존 동작을 유지할 수 있다.
- 통합 LLM이 아직 활성화되지 않은 환경에서 사용한다.

### LLM 연결 모드

- 확정적인 새 규칙은 읽기로 변환한다.
- 유보 판정 표면은 숫자가 포함된 원문 형태로 유지한다.
- 후속 통합 LLM이 잔여 숫자·알파벳·기호를 처리한다.

`DEFER`를 실제 출력에 반영하는 시점은 통합 Prompt V1 경로와 최종 잔여 문자 검증기가 안정화된 이후여야 한다.

# 4. 규칙 판정의 내부 결과 유형

각 숫자·단위 owner는 논리적으로 다음 네 가지 결과 중 하나를 반환해야 한다.

## 4.1 확정 변환

규칙만으로 읽기가 충분히 확정된 상태다.

예:

```text
3번 버스 → 삼 번 버스
5분 뒤 → 오 분 뒤
자동차 3대 → 자동차 세 대
평점 3점 → 평점 삼 점
```

결과가 확정되면 해당 표면은 이후 일반 숫자 규칙이나 다른 단위 owner가 다시 처리하지 않는다.

## 4.2 문맥 판단 유보

숫자·단위 표면은 식별됐지만 의미가 둘 이상 가능하다.

예:

```text
3번 확인했다
3점이 공개됐다
3대가 남았다
3권부터 읽었다
```

이 경우:

- 출력 문자열은 원문 그대로 유지한다.
- 숫자 부분만 변환하지 않는다.
- 단위 부분만 변환하지 않는다.
- 이후의 일반 숫자 fallback으로 넘기지 않는다.
- 다른 단위 owner가 재처리하지 않는다.
- 표면 전체를 하나의 유보 단위로 종료한다.

## 4.3 절대 보존

발음변환 자체가 금지된 영역이다.

예:

```text
H100_test_v2.json
https://example.com
SKU-3B
user_id3
```

절대 보존과 문맥 판단 유보는 반드시 구분해야 한다.

- 절대 보존: LLM도 변경하면 안 됨
- 문맥 판단 유보: LLM이 반드시 읽기를 판단해야 함

## 4.4 비대상

현재 owner가 처리할 표면이 아니므로 다음 우선순위의 owner로 넘긴다.

# 5. 문맥 판단 유보의 종료성

문맥 판단 유보는 단순한 “실패”가 아니다.

유보 owner가 표면을 인식했다면 해당 표면은 이미 처리 경로가 결정된 것이다.

따라서 다음 동작을 금지한다.

- 숫자만 일반 한자어 수사로 바꾸기
- 단위만 기존 counter 규칙으로 처리하기
- 숫자와 단위를 서로 다른 owner가 나누어 처리하기
- 유보된 결과를 다시 generic numeric suffix로 처리하기
- 공백 유무에 따라 같은 표면이 다른 경로로 재진입하기

예:

```text
3번 확인했다
```

유보 결과는 반드시 그대로 `3번 확인했다`여야 한다.

다음은 금지한다.

```text
삼번 확인했다
삼 번 확인했다
3 번 확인했다
```

후자의 읽기가 문맥상 맞을 수도 있지만, 이 단계에서는 LLM이 판단하도록 원문을 그대로 유지해야 한다.

---

# 6. 전체 소비 범위

유보하거나 확정하는 경우 숫자와 단위만 부분적으로 인식해서는 안 된다.

다음 요소까지 포함해 하나의 의미 표면으로 판단한다.

- 숫자
- 단위
- 숫자와 단위 사이의 기존 공백
- 단위에 붙은 조사
- 단위에 붙은 수량 관련 보조 표현
- 단위와 직접 결합한 접사

예:

```text
3번이
3번을
3번만
3번씩
3대가
3대째
3조로
3점에서
```

단, 조사와 어미 자체의 철자를 바꾸지 않는다.

판정 범위에 조사를 포함한다는 것은 조사까지 발음변환한다는 뜻이 아니라, 조사에 의해 의미가 확정되는지를 함께 본다는 뜻이다.

# 7. 새 규칙을 승인하는 기준

새 규칙은 다음 조건을 모두 충족할 때만 확정 변환 규칙으로 추가한다.

## 7.1 필수 조건

1. 표면 구조가 명확하다.
2. 숫자와 단위의 경계가 명확하다.
3. 의미를 결정하는 직접적인 앞말이나 뒷말이 있다.
4. 짧은 로컬 문맥만으로 의미를 확정할 수 있다.
5. 반대 의미의 문맥을 명시적으로 차단할 수 있다.
6. 숫자 전체와 단위 전체를 한 번에 처리할 수 있다.
7. 보호 구간과 충돌하지 않는다.
8. 소수·부호·선행 0 등 비표준 수량 표면을 잘못 처리하지 않는다.
9. 기존 숫자 renderer를 그대로 사용할 수 있다.
10. 같은 표면에 다른 자연스러운 읽기가 남지 않는다.

## 7.2 확정 규칙으로 승인하면 안 되는 경우

다음 중 하나라도 해당하면 유보한다.

- 동사의 의미를 폭넓게 추론해야 함
- 앞 명사의 상위 의미 범주를 추론해야 함
- 문장 전체의 주어와 목적어 관계를 이해해야 함
- 생략된 명사를 복원해야 함
- 상식이나 세계 지식이 필요함
- 둘 이상의 읽기가 모두 자연스러움
- 긴 거리의 앞 문장을 참조해야 함
- 알려지지 않은 명사에 규칙을 일반화해야 함
- 특정 뉴스 분야에서만 의미가 확정됨
- 형태는 같지만 도메인에 따라 읽기가 달라짐

# 8. 문맥 사용 범위

규칙 기반 엔진은 의미 추론기가 아니다.

새 규칙은 다음 범위 안에서만 문맥을 사용한다.

## 8.1 허용하는 문맥

- 같은 어절
- 숫자·단위의 바로 앞 어절
- 숫자·단위의 바로 뒤 어절
- 숫자·단위에 직접 붙은 조사와 접사
- 등록된 고정 구
- 등록된 앞 명사와 뒤 동사의 정확한 조합
- 기존 owner가 이미 분류한 구조 정보

## 8.2 사용하지 않는 문맥

- 두 문장 이상 떨어진 문맥
- 대명사의 지시 대상
- 생략된 주어나 목적어
- 기사 제목과 본문의 연계
- 발화자의 의도
- 확률적 의미 분류
- 미등록 명사의 자동 의미 분류
- 임베딩 유사도
- 주변 단어의 부분 문자열 유사도

# 9. 숫자 형식 공통 제한

새로운 문맥형 단위 규칙은 기본적으로 다음 표면만 확정 처리한다.

- 일반적인 양의 정수
- 현재 숫자 parser가 완전하게 해석할 수 있는 표면
- 단위와 직접 결합하거나 정상적인 공백 한 칸으로 결합한 표면

다음 표면은 해당 규칙이 별도로 명시하지 않는 한 확정하지 않는다.

- 소수
- 음수
- 양수 기호가 붙은 숫자
- 선행 0이 있는 숫자
- 잘못된 쉼표가 포함된 숫자
- 범위
- 비율
- 분수
- 숫자와 알파벳이 섞인 표면
- 코드형 문자열
- 괄호·슬래시·콜론과 결합한 복합 표면

예:

```text
03번
+3번
-3점
3.5대
01분
1,00조
3A번
```

이 표면들은 기존의 더 구체적인 owner가 처리하지 않는 한 유보하거나 기존 보호 정책을 따른다.

# 10. 숫자 읽기 생성 원칙

새 owner가 숫자 읽기 변환 방식을 직접 새로 정의해서는 안 된다.

다음은 현재 엔진의 기존 숫자 생성 정책을 그대로 사용한다.

- 한자어 정수 읽기
- 고유어 수사 읽기
- 고유어 축약형
- 20·30대 수사형
- 40 이상 임계값
- 100 이상 처리
- 단위와의 공백
- 조사 결합
- 소수 읽기
- 선행 0 처리
- 숫자 provenance

현재 counter 정책은 단위에 따라 고유어·혼합형·한자어를 구분하고, 혼합형 counter에서 일정 숫자 이상을 한자어로 처리한다. 새 규칙도 이 renderer를 재사용해야 하며 별도의 수사 변환 체계를 만들면 안 된다. fileciteturn2file0L24-L94

# 11. 관리 사전과의 역할 분리

문맥형 숫자·단위 규칙을 관리 사전에 넣지 않는다.

관리 사전은 다음 용도로만 유지한다.

- 고정된 어휘 표면
- 정확한 지정 읽기
- 문맥과 무관한 예외
- 가장 긴 정확 일치가 가능한 항목

다음과 같은 일반 규칙을 사전으로 만들면 안 된다.

- 사람 명사 뒤의 모든 `N분`
- 작품 명사 뒤의 모든 `N점`
- 동작 동사 앞의 모든 `N번`
- 기계 명사 뒤의 모든 `N대`
- 문서 명사 뒤의 모든 `N부`

관리 사전 정책은 고정 어휘 예외를 대상으로 하며, 인접한 숫자나 문자를 근거로 일반 문맥 규칙을 추론하지 않도록 제한한다. fileciteturn3file0L13-L21 fileciteturn3file0L33-L50

문맥형 숫자·단위는 별도의 명시적 규칙군과 독립된 anchor 목록으로 관리한다.

# 12. 규칙 우선순위 설계

전체 우선순위는 다음 순서를 따른다.

## 12.1 공통 우선순위

1. 절대 보호 구간
2. 코드형·식별형 표면
3. 기존의 가장 구체적인 날짜·전화번호·통화·온도·범위·분수 owner
4. 기존의 점수·비율·관계 owner
5. 기존의 명시적 서수·차수·주소·위치 owner
6. 새로 추가하는 확정적 문맥형 숫자·단위 owner
7. 새로 추가하는 숫자·단위 유보 owner
8. 기존 generic numeric suffix owner
9. 기존 generic counter owner
10. 기존 일반 숫자 fallback
11. 최종 보존

기존 priority 표의 구체적 owner가 generic numeric suffix와 counter보다 먼저 실행되는 구조를 유지한다. fileciteturn3file2L141-L202

## 12.2 유보 owner의 위치

유보 owner는 다음 두 조건을 모두 만족해야 한다.

- 해당 단위의 구체적이고 안전한 확정 owner 뒤
- 해당 단위가 흘러 들어갈 기존 generic owner 앞

즉:

```text
안전한 확정
→ 모호하면 유보
→ generic 처리 차단
```

유보 owner를 너무 앞에 두어 기존의 확정적인 날짜·시간·점수·서수 규칙까지 막으면 안 된다.

# 13. 단위별 상세 설계

## 13.1 `분`

현재 정책은 일반적인 `N분`을 시간·기간의 한자어 수사로 처리하고, 사람을 높여 세는 `분`은 별도 범위로 처리하지 않는다. fileciteturn2file2L460-L492

### 확정 처리: 시간·기간

다음과 같이 시간 의미를 직접 나타내는 표현은 기존 정책을 유지한다.

- `N분 뒤`
- `N분 전`
- `N분 동안`
- `N분 이내`
- `N분 이상`
- `N분 이하`
- `N분 소요`
- `소요 시간 N분`
- `N분 N초`
- `N시 N분`
- 시각 표기에서 파생된 `N분`

예:

```text
5분 뒤 → 오 분 뒤
5분 동안 → 오 분 동안
3분 20초 → 삼 분 이십 초
```

기존 canonical이 `오분`처럼 붙여 쓰는 정책이라면 새 규칙도 기존 spacing을 그대로 따른다.

### 확정 처리: 높임 사람 수

다음 조건을 모두 만족할 때만 고유어 사람 수로 처리한다.

1. 숫자 바로 앞 또는 짧은 고정 구조 안에 등록된 사람 명사가 있다.
2. 해당 명사가 실제 인원 집합을 나타낸다.
3. 시간 관련 단어가 주변에 없다.
4. 숫자는 일반 정수다.
5. 선행 0·부호·소수가 없다.

초기 등록 후보:

- 손님
- 고객
- 내빈
- 참석자
- 참가자
- 지원자
- 후보자
- 위원
- 심사위원
- 선생님
- 교수님
- 어르신
- 환자
- 승객

안전한 구조 예:

```text
손님 5분이 도착했다
내빈은 총 5분이다
참석자 12분을 모셨다
```

### 유보

다음은 원문을 유지한다.

- 사람 명사 없이 독립적으로 나온 `N분`
- 시간과 사람 의미가 모두 가능한 표현
- `N분께`
- `N분 정도`
- `N분가량`
- 선행 문장에서만 사람 의미를 알 수 있는 표현
- 등록되지 않은 사람 명사와 결합한 표현

예:

```text
5분이 남았다
앞에 5분이 있다
5분께 연락했다
```

현재 정책에서도 `6분께` 같은 표면은 사람 수 의미가 확정되지 않아 보존 대상으로 분류되어 있다. fileciteturn2file3L677-L682

### 우선순위

```text
명시적 시각
→ 명시적 기간
→ 확정적 사람 수
→ 모호한 분 유보
→ 기존 일반 분 처리
```

---

## 13.2 `초`

`초`는 기본적으로 시간·기간의 한자어 수사로 유지한다.

### 확정 처리

- `N초 뒤`
- `N초 전`
- `N초 동안`
- `N분 N초`
- 초 단위 기록
- 경기 시간
- 처리 시간

### 유보 또는 기존 다른 owner 우선

- 주소의 초성·문자 기호
- 코드형 표면
- `초`가 다른 단어의 일부인 경우
- 소수·범위·부호가 기존 owner로 처리되지 않은 경우

`초`는 `분`보다 사람 단위와 충돌하지 않으므로 별도의 광범위한 의미 유보는 만들지 않는다.

## 13.3 `번`

현재 `3번`은 generic numeric suffix 계열에서 처리된다. fileciteturn3file2L185-L188

이번 업데이트에서는 번호와 횟수를 분리한다.

### 확정 처리: 번호·식별자

숫자 바로 뒤 또는 고정 구조에 다음 명사가 있으면 한자어 수사로 처리한다.

- 버스
- 출구
- 문제
- 문항
- 질문
- 후보
- 좌석
- 객실
- 창구
- 게이트
- 트랙
- 채널
- 노선
- 테이블
- 파일
- 항목

예:

```text
3번 버스 → 삼 번 버스
3번 문제 → 삼 번 문제
3번 출구 → 삼 번 출구
```

`제N번`과 같이 서수가 명시된 구조도 한자어로 처리한다.

### 확정 처리: 실제 횟수

다음과 같이 횟수 의미를 명시하는 구조에서만 고유어 수사로 처리한다.

- `총 N번`
- `모두 N번`
- `N번씩`
- `N번이나`
- `N번 반복`
- `N번 재시도`
- `N번 방문`
- `N번 시도`
- `N번 호출`
- `N번 클릭`
- `N번 재생`

동사 하나만으로 판단하지 말고, 등록된 동작 명사 또는 반복 표지가 있어야 한다.

예:

```text
총 3번 시도했다 → 총 세 번 시도했다
3번씩 반복했다 → 세 번씩 반복했다
3번 재생했다 → 세 번 재생했다
```

### 유보

다음은 유보한다.

```text
3번 확인했다
3번 말했다
3번 선택했다
3번 처리했다
3번이 맞다
3번부터 시작한다
```

이 표현은 횟수, 번호, 선택지 식별자 중 둘 이상이 가능하다.

### 우선순위

```text
명시적 서수
→ 확정 번호
→ 확정 횟수
→ 번 의미 유보
→ generic numeric suffix 차단
```

## 13.4 `점`

현재 `점`은 기본적으로 한자어 counter로 처리된다. fileciteturn2file2L570-L580

### 확정 처리: 점수·평가값

다음 anchor가 있으면 한자어로 처리한다.

- 점수
- 평점
- 만점
- 득점
- 실점
- 감점
- 가점
- 별점
- 획득
- 기록
- 차이
- 격차
- 평균
- 평가

예:

```text
평점 3점 → 평점 삼 점
3점 차이 → 삼 점 차이
3점을 획득했다 → 삼 점을 획득했다
```

소수 `N.N점`은 항상 한자어 소수 읽기를 유지한다.

```text
3.5점 → 삼쩜오 점
```

### 확정 처리: 작품·물품 수량

다음 조건을 모두 만족해야 고유어 수사로 처리한다.

1. 등록된 수량 대상 명사가 숫자와 직접 연결된다.
2. 점수 관련 anchor가 없다.
3. 실제 물품 수량을 나타내는 동사 또는 수량 구조가 있다.

초기 대상 명사:

- 작품
- 출품작
- 전시품
- 미술품
- 유물
- 문화재
- 소장품
- 물품
- 상품
- 수집품

수량 동사:

- 전시
- 공개
- 출품
- 기증
- 소장
- 선정
- 판매
- 반입
- 확보

예:

```text
작품 3점을 전시했다 → 작품 세 점을 전시했다
유물 3점을 공개했다 → 유물 세 점을 공개했다
```

### 유보

```text
새로 들어온 3점
선정된 것은 3점이다
3점이 공개됐다
이번 3점
```

앞뒤 문맥을 넓게 해석해야 하는 경우에는 유보한다.

### 우선순위

```text
점수 관계
→ 소수 점수
→ 확정 물품 수량
→ 점 의미 유보
→ 기존 generic 점
```

## 13.5 `대`

현재 `대`는 점수 관계, 기계 수량, 세대·연령대·주요 항목 등 여러 의미가 충돌한다. 현행 정책은 점수 관계를 우선하고, 일부 등록된 기계 명사에서만 낮은 숫자의 고유어 수량을 허용하며, 해결되지 않는 낮은 숫자 표면을 보존한다. fileciteturn2file1L243-L305 fileciteturn2file1L307-L358

### 기존 유지: 점수·비율 관계

```text
3대2
3 대 2
```

기존 점수 관계 owner를 그대로 우선한다.

### 확정 처리: 기계·차량 수량

현재 승인된 명사 registry를 유지하고, 실제 운영 corpus에서 검증된 명사만 추가한다.

현재 핵심 범주:

- 자동차
- 차량
- 장비
- 버스
- 서버
- 카메라

확장 검토 대상:

- 승용차
- 트럭
- 택시
- 열차
- 기차
- 오토바이
- 자전거
- 드론
- 로봇
- 컴퓨터
- 노트북
- 모니터
- 프린터
- 스마트폰
- 태블릿
- 냉장고
- 세탁기
- 텔레비전

추가 조건:

- 명사와 `N대`가 같은 명사구에 있어야 한다.
- 숫자와 단위가 수량을 나타내야 한다.
- 연령대·세대·주요 항목 의미가 아니어야 한다.
- 등록 명사가 다른 의미로 쓰이는 고유명사이면 처리하지 않는다.

### 확정 처리: 세대

다음 구조는 한자어로 처리한다.

- `N대째`
- 가족·가문·가계·가업·집안·왕조·세습과 직접 결합한 `N대`

예:

```text
가업을 3대째 이어 왔다 → 가업을 삼 대째 이어 왔다
가족 3대가 함께 살았다 → 가족 삼 대가 함께 살았다
```

`N대째`는 기계 수량에서도 “세 번째 기계” 의미가 될 수 있으므로 숫자 자체는 한자어로 읽는 것이 안정적이다.

### 확정 처리: 연령대

다음 조건을 모두 만족하면 한자어로 처리한다.

- 숫자가 10의 배수
- 연령 관련 명사가 직접 뒤따름
- 또는 `초반·중반·후반`이 직접 뒤따름

연령 관련 명사:

- 남성
- 여성
- 청년
- 직장인
- 소비자
- 유권자
- 환자
- 인구
- 세대
- 연령층

예:

```text
20대 남성 → 이십 대 남성
30대 초반 → 삼십 대 초반
```

### 확정 처리: 주요 항목 표현

`3대 과제`, `5대 원칙`과 같은 표현은 자유 명사 추론으로 처리하지 않는다.

검증된 전체 구 또는 승인 명사와 직접 결합한 경우에만 한자어로 처리한다.

초기 검토 명사:

- 과제
- 원칙
- 목표
- 전략
- 정책
- 산업
- 강국
- 미항
- 명소
- 요인
- 쟁점
- 축
- 분야
- 브랜드

실제 적용은 개별 명사별 대조 corpus를 통과한 항목만 허용한다.

### 유보

```text
3대가 남았다
새 장비 3대
중요한 3대
이번 3대
3대 과제
```

승인된 직접 결합 조건을 만족하지 못하면 유보한다.

현재 정책도 `3대`, `20대가`, `5대 과제`, `20대 남성`, `가족 3대`, `3대째`, `1.5대`처럼 해결되지 않은 표면을 의미 단위로 보존하도록 설계되어 있다. fileciteturn2file3L772-L815

### 우선순위

```text
점수 관계
→ 연령대
→ 세대·N대째
→ 승인된 주요 항목
→ 승인된 기계 수량
→ 대 의미 유보
→ 기존 임계값 처리
```

## 13.6 `조`

`조`는 큰 수, 법조문, 그룹 수량, 그룹 번호가 충돌한다.

### 확정 처리: 큰 수·금액

다음은 한자어 큰 수로 처리한다.

- `N조 원`
- `N조원`
- 예산·매출·자산·부채·투자·규모와 직접 결합한 `N조`
- 기존 큰 수 구조

예:

```text
3조 원 → 삼조 원
예산 3조 → 예산 삼조
```

### 확정 처리: 법조문

```text
제3조
법률 제3조
제3조 제2항
```

한자어 서수·조문 읽기를 적용한다.

### 확정 처리: 그룹 수량

다음과 같이 실제 그룹 개수를 명시하는 구조에서만 고유어 수사로 처리한다.

- `총 N조`
- `모두 N조`
- `N조로 나누다`
- `N조로 편성하다`
- `N조로 구성하다`
- `N조를 배정하다`
- `N조를 만들다`

예:

```text
학생을 3조로 나눴다 → 학생을 세 조로 나눴다
총 3조를 편성했다 → 총 세 조를 편성했다
```

### 유보

```text
3조가 발표했다
3조에 배정됐다
앞의 3조
3조부터 시작한다
```

그룹 번호인지 그룹 수량인지 명확하지 않으면 유보한다.

### 특별 우선순위

그룹 수량 owner는 기존 큰 수 atomic owner보다 먼저 실행해야 한다.

```text
법조문·금액 명시
→ 그룹 수량
→ 조 의미 유보
→ 큰 수 일반 owner
```

단, `N조 원`과 금융 anchor는 그룹 수량보다 우선한다.

## 13.7 `부`

`부`는 복사본·문서 수량, 행사 순서, 책의 부, 연작 구성이 충돌한다.

### 확정 처리: 순서·구성

다음은 한자어로 처리한다.

- `제N부`
- `N부작`
- `행사 N부`
- `공연 N부`
- `보고서 제N부`
- `책의 N부`

예:

```text
제3부 → 제삼부
3부작 → 삼부작
행사 3부 → 행사 삼 부
```

### 확정 처리: 문서 복사본 수량

다음 조건을 모두 만족하면 고유어로 처리한다.

1. 승인된 문서·인쇄물 명사가 있다.
2. 실제 복사본 수량을 나타낸다.
3. 순서·구성 의미가 아니다.

대상 명사:

- 신문
- 서류
- 문서
- 보고서
- 신청서
- 계약서
- 책자
- 인쇄물
- 안내문
- 자료집
- 원고

강한 수량 동사:

- 인쇄
- 복사
- 제출
- 배포
- 준비
- 발급
- 보관

예:

```text
서류 3부를 제출했다 → 서류 세 부를 제출했다
신문 3부를 준비했다 → 신문 세 부를 준비했다
```

### 유보

```text
자료 3부
오늘 3부
새로 만든 3부
3부가 남았다
```


## 13.18 '가지'

## `가지` 숫자 읽기 규칙

`가지`는 사물·방법·종류·선택지 등을 세는 의존 명사다.

일반적인 양의 정수와 결합한 `숫자+가지`는 한자어 수사가 아니라 고유어 수사로 읽는다.

따라서 다음 변환을 적용한다.

```text
1가지 → 한 가지
2가지 → 두 가지
3가지 → 세 가지
4가지 → 네 가지
5가지 → 다섯 가지
10가지 → 열 가지
20가지 → 스무 가지
21가지 → 스물한 가지
30가지 → 서른 가지
40가지 → 마흔 가지
50가지 → 쉰 가지
60가지 → 예순 가지
70가지 → 일흔 가지
80가지 → 여든 가지
90가지 → 아흔 가지
99가지 → 아흔아홉 가지
```

`4가지`를 `사가지`로 읽어서는 안 된다.

---

### 확정 처리 범위

다음 조건을 모두 만족하면 `가지` 수량 owner가 표면을 확정 처리한다.

1. 보호 구간 밖에 있다.
2. 숫자와 `가지`가 직접 결합하거나 ASCII 공백 한 칸으로 결합한다.
3. 숫자가 정상적으로 해석 가능한 1 이상 99 이하의 정수다.
4. 부호·소수점·선행 0·잘못된 쉼표가 없다.
5. 범위·분수·코드·식별자 표면의 일부가 아니다.
6. `가지`가 독립된 의존 명사로 사용됐다.
7. 숫자와 `가지` 사이에 다른 문자가 없다.

입력의 공백 유무와 관계없이 출력은 고유어 수사와 `가지` 사이에 현재 counter canonical에 따른 공백을 둔다.

```text
4가지 → 네 가지
4 가지 → 네 가지
```

---

### 조사와 어미 결합

`가지` 뒤에 조사나 서술격 표현이 붙어도 숫자 읽기는 동일하게 처리한다.

```text
4가지가 → 네 가지가
4가지를 → 네 가지를
4가지는 → 네 가지는
4가지도 → 네 가지도
4가지만 → 네 가지만
4가지의 → 네 가지의
4가지로 → 네 가지로
4가지와 → 네 가지와
4가지에서 → 네 가지에서
4가지까지 → 네 가지까지
4가지다 → 네 가지다
4가지입니다 → 네 가지입니다
```

조사와 어미의 철자 및 문법적 기능은 변경하지 않는다.

---

### 0과 100 이상의 수

`0가지`는 고유어 수사가 없으므로 한자어 수사를 사용한다.

```text
0가지 → 영 가지
```

100 이상의 수는 이번 규칙에서 새로운 숫자 생성 방식을 정의하지 않고, 기존 대수 counter 읽기 정책을 따른다.

최소한 다음 형태는 기존 한자어 큰 수 renderer를 사용해 처리할 수 있다.

```text
100가지 → 백 가지
200가지 → 이백 가지
1000가지 → 천 가지
```

100 이상의 수에서 일의 자리와 십의 자리의 고유어 혼합 여부는 기존 엔진의 전체 counter 정책과 일치시켜야 하며, `가지` 규칙만 별도의 수사 조합 방식을 만들지 않는다.

---

### 범위 표현

범위 owner가 `가지` owner보다 먼저 실행되어야 한다.

```text
3~4가지
3∼4가지
3-4가지
```

위 표면은 `가지` owner가 숫자 하나만 부분 처리해서는 안 된다.

기존 범위 정책이 해당 표면을 완전히 처리할 수 있으면 범위 owner가 양 끝 숫자와 단위를 함께 처리한다.

예상 읽기 정책이 `에서`를 사용하는 경우:

```text
3~4가지 → 세 가지에서 네 가지
```

범위 형식을 안전하게 해석할 수 없으면 표면 전체를 원문으로 유지하여 후속 LLM에 넘긴다.

---

### 처리하지 않고 유보할 표면

다음 표면은 `가지` 고유어 counter 규칙이 확정 처리하지 않는다.

```text
01가지
+4가지
-4가지
1.5가지
1,00가지
4A가지
제4가지
```

처리 원칙:

- 숫자 일부만 변환하지 않는다.
- `가지`만 분리하지 않는다.
- 표면 전체를 원문 그대로 유지한다.
- 일반 숫자 fallback이 숫자만 한자어로 변환하지 못하도록 재진입을 차단한다.
- 후속 통합 LLM의 처리 대상으로 남긴다.

금지 출력:

```text
01가지 → 영일 가지
+4가지 → 플러스 사가지
1.5가지 → 일쩜오가지
제4가지 → 제사가지
```

---

### 보호 구간

다음과 같은 보호 구간 내부에서는 `가지` 규칙을 적용하지 않는다.

```text
`4가지`
/path/4가지/file
{"value":"4가지"}
item_4가지
4가지.json
https://example.com/4가지
```

보호 구간의 문자·숫자·공백은 원문 그대로 유지한다.

---

### 단어 경계 보호

다음처럼 `가지`가 다른 단어의 일부인 경우에는 숫자 counter 규칙으로 처리하지 않는다.

- 코드형 문자열
- 파일명
- 변수명
- 고유 식별자
- 숫자와 `가지` 사이에 다른 문자가 있는 표면
- `가지` 이후 문자가 결합해 다른 어휘 또는 식별자를 형성하는 표면

단, 정상적인 조사·어미 결합은 처리 대상이다.

```text
4가지를 → 처리
4가지입니다 → 처리
4가지형코드 → 유보 또는 보호
```

---

### 규칙 우선순위

`가지` owner는 다음 순서에 배치한다.

```text
절대 보호 구간
→ 코드·URL·파일명·식별자
→ 범위·분수·소수 등 기존 구체적 숫자 owner
→ 가지 고유어 수량 owner
→ 비정상 또는 미지원 숫자+가지 유보 owner
→ generic numeric suffix
→ 일반 숫자 fallback
```

`가지` 고유어 수량 owner는 일반 숫자 fallback보다 반드시 먼저 실행해야 한다.

그렇지 않으면 다음과 같은 오류가 발생한다.

```text
4가지
→ 일반 숫자 fallback이 4를 사로 변환
→ 사가지
```

---

### 내부 판정 유형

정상적인 정수 수량은 확정 변환으로 판정한다.

```text
표면: 4가지
의미: kind_or_item_count
수사 체계: native
예상 읽기: 네 가지
판정: 확정 변환
```

비정상 형식이나 미지원 형식은 문맥 판단 유보로 판정한다.

```text
표면: 1.5가지
의미: number_plus_gaji_unresolved
예상 후보: 일쩜오 가지
판정: 유보
서비스 문자열: 1.5가지
```

내부 판정 정보는 서비스 출력에 포함하지 않는다.

---

### 필수 회귀 테스트

#### 기본 수사

```text
1가지 → 한 가지
2가지 → 두 가지
3가지 → 세 가지
4가지 → 네 가지
10가지 → 열 가지
20가지 → 스무 가지
21가지 → 스물한 가지
40가지 → 마흔 가지
99가지 → 아흔아홉 가지
100가지 → 기존 대수 counter 정책
```

#### 조사와 어미

```text
4가지가 → 네 가지가
4가지를 → 네 가지를
4가지로 → 네 가지로
4가지만 → 네 가지만
4가지입니다 → 네 가지입니다
```

#### 공백

```text
4가지 → 네 가지
4 가지 → 네 가지
```

#### 여러 표면

```text
문제에는 3가지 원인과 4가지 해결책이 있습니다.
→ 문제에는 세 가지 원인과 네 가지 해결책이 있습니다.
```

#### 기존 한글 표현 보존

```text
네 가지 방법 → 네 가지 방법
여러 가지 방법 → 여러 가지 방법
몇 가지 방법 → 몇 가지 방법
한 가지 방법 → 한 가지 방법
```

이미 한글 수사로 처리된 표현은 다시 처리하지 않는다.

#### 비정상 형식 유보

```text
01가지 → 원문 유지
+4가지 → 원문 유지
-4가지 → 원문 유지
1.5가지 → 원문 유지
1,00가지 → 원문 유지
4A가지 → 원문 유지
```

#### 부분 처리 금지

다음 출력이 발생해서는 안 된다.

```text
사가지
사 가지
4 가지
네가지
일쩜오가지
```

단, `네가지`의 띄어쓰기 정책이 기존 엔진 canonical에서 별도로 정해져 있다면 전체 counter 정책과 일치시킨다. 권장 canonical은 `네 가지`다.

---

### 기존 counter 목록 보완

현재 안정적인 counter 목록에 `가지`를 추가한다.

```text
명
개
마리
가지
권
장
대
판
회
개월
학년
학기
```

단, `가지`는 기존 일부 hybrid counter의 `1~39 고유어, 40 이상 한자어` 정책을 기계적으로 적용하지 않는다.

`가지`는 1 이상 99 이하에서 고유어 수사가 자연스러우므로 별도의 counter 수사 범위를 명시한다.

```text
40가지 → 마흔 가지
```

다음과 같이 읽지 않는다.

```text
40가지 → 사십 가지
```

100 이상의 읽기는 기존 대수 counter 정책에 위임한다.

---

### 완료 조건

`가지` 규칙은 다음 조건을 모두 만족해야 한다.

1. `4가지`가 `네 가지`로 출력된다.
2. `4가지를`, `4가지로`, `4가지입니다`가 올바르게 처리된다.
3. 기존 한글 표현 `네 가지`는 변경되지 않는다.
4. 범위 표면을 부분 변환하지 않는다.
5. 부호·소수·선행 0 표면을 부분 변환하지 않는다.
6. 보호 구간 내부를 변경하지 않는다.
7. 일반 숫자 fallback이 `4가지`를 `사가지`로 만들지 못한다.
8. 서비스 문자열에 내부 판정 정보가 노출되지 않는다.
9. 소스 테스트와 실제 배포 패키지 probe에서 동일한 결과가 나온다.

---

# 14. 기존에 안정적인 counter의 처리

다음과 같이 현재 의미 충돌이 적고 기존 정책에서 안정적으로 처리되는 counter는 기존 로직을 유지한다.

- 명
- 개
- 마리
- 권
- 장
- 대
- 판
- 회
- 개월
- 학년
- 학기

단, 앞 절에서 별도의 의미 충돌 규칙이 지정된 `권·장·대·판`은 새 구체적 owner와 유보 owner를 먼저 적용한다.

새로운 counter를 대량으로 일괄 추가하지 않는다.

새 counter는 다음 검증을 거친 뒤 개별적으로 추가한다.

- 일반 명사와의 동형 충돌
- 접사와의 충돌
- 단위 의미의 수사 체계
- 1–39와 40 이상 읽기
- 100 이상 읽기
- 소수 허용 여부
- 단독 표면의 의미
- 조사 결합
- 코드형 문자열 충돌

# 15. 후보 읽기 내부 생성

이번 단계에서는 후보 읽기를 서비스 문자열에 출력하지 않지만, shadow 검증을 위해 내부적으로 생성한다.

## 15.1 후보가 필요한 대상

- `분`
- `번`
- `점`
- `대`
- `조`
- `부`
- `동`
- `호`
- `판`
- `단`
- `등`
- `척`
- `장`
- `권`
- `편`
- `층`

## 15.2 후보 생성 원칙

후보는 기존 숫자 renderer와 단위 spacing 정책으로 생성한다.

예:

| 표면 | 의미 후보 1 | 의미 후보 2 |
|---|---|---|
| `3번` | `세 번`—횟수 | `삼 번`—번호 |
| `5분` | `다섯 분`—사람 수 | `오 분`—시간 |
| `3점` | `세 점`—물품 수량 | `삼 점`—점수 |
| `3대` | `세 대`—기계 수량 | `삼 대`—세대·연령·주요 항목 |
| `3조` | `세 조`—그룹 수량 | `삼조` 또는 `삼 조`—큰 수·번호 |
| `3부` | `세 부`—복사본 | `삼 부`—구성 순서 |
| `3동` | `세 동`—건물 수량 | `삼 동`—위치·번호 |
| `3호` | `세 호`—가구 수량 | `삼 호`—식별 번호 |
| `3판` | `세 판`—경기 횟수 | `삼 판`—판차 |
| `3단` | `세 단`—적층 수량 | `삼 단`—등급·기어 |
| `3등` | `세 등`—조명 수량 | `삼 등`—순위 |
| `3척` | `세 척`—선박 수량 | `삼 척`—길이 |
| `3장` | `세 장`—물품 수량 | `삼 장`—장 번호 |
| `3권` | `세 권`—책 수량 | `삼 권`—권 번호 |
| `3편` | `세 편`—작품 수량 | `삼 편`—편 번호 |
| `3층` | `세 층`—이동·개수 | `삼 층`—위치·층 번호 |

후보는 LLM이 나중에 자유 생성하지 않도록 가능한 의미별 정답 형태를 미리 검증하는 용도로 사용한다.

## 15.3 후보를 생성하지 않는 경우

다음은 후보 생성보다 절대 보존 또는 기존 owner를 우선한다.

- 코드
- URL
- 제품 식별자
- 소수인데 단위별 정책이 불명확한 경우
- 잘못된 숫자 표면
- 세 가지 이상의 해석이 있어 후보를 안정적으로 열거할 수 없는 경우
- 현재 숫자 renderer가 처리할 수 없는 형식

# 16. 내부 shadow 기록 항목

서비스 출력과 분리된 shadow 기록에는 최소한 다음 정보가 필요하다.

| 항목 | 의미 |
|---|---|
| 규칙 버전 | 어떤 규칙 집합이 판정했는지 |
| 입력 표면 | 원문 숫자·단위 문자열 |
| 입력 내 위치 | 동일 표면을 구분하기 위한 범위 |

| 판정 결과 | 확정·유보·절대 보존·비대상 |
| 확정 의미 | 시간·횟수·번호·점수·수량 등 |
| 확정 읽기 | 실제 적용하거나 예상한 읽기 |
| 후보 읽기 | 유보일 때 가능한 읽기 |
| 긍정 근거 | 일치한 명사·접사·구조 |
| 차단 근거 | 소수·부호·코드·경쟁 의미 등 |
| 실행 우선순위 | 어떤 owner가 먼저 claim했는지 |
| 재진입 차단 여부 | 다른 owner가 처리하지 않았는지 |
| 기존 엔진 결과 | 업데이트 전 결과 |
| 새 규칙 예상 결과 | shadow 판정 결과 |
| 실제 서비스 출력 | 호환 모드의 최종 문자열 |

원문 전체를 장기 저장하기 어려운 환경에서는 필요한 로컬 문맥과 비식별화된 표면만 보관한다.

# 17. Shadow 검증 단계

## 17.1 1단계: 판정만 기록

- 실제 출력은 기존 엔진 결과를 사용한다.
- 새 owner는 확정·유보 판정만 기록한다.
- 기존 결과와 새 결과의 차이를 수집한다.
- 단위별 오판 유형을 분류한다.

## 17.2 2단계: 확정 변환만 활성화

- 정확도가 검증된 확정 규칙만 실제 출력에 반영한다.
- 유보 판정은 계속 shadow에만 기록한다.
- 기존 서비스 회귀를 집중 점검한다.

## 17.3 3단계: 유보 차단 활성화

통합 Prompt V1이 실제 요청 경로에 안정적으로 연결된 이후 활성화한다.

- 모호한 표면은 숫자 형태로 유지한다.
- generic fallback 재처리를 차단한다.
- 후속 LLM이 잔여 숫자를 한국어 읽기로 변환한다.
- LLM 실패 시 raw 숫자가 바로 TTS에 전달되지 않도록 최종 검증 경로가 있어야 한다.

## 17.4 4단계: 내부 후보 품질 검증

- LLM이 문맥에서 선택한 읽기와 shadow 후보를 비교한다.
- 후보 누락률을 측정한다.
- 후보가 항상 두 개일 필요는 없다.
- 한 의미만 남으면 유보 규칙이 아니라 확정 규칙으로 승격할 수 있다.

# 18. 테스트 설계

각 새 규칙은 최소 다음 테스트 유형을 모두 포함해야 한다.

## 18.1 긍정 테스트

- 확정 고유어 수사
- 확정 한자어 수사
- 공백 없는 표면
- 공백 있는 표면
- 조사 결합
- 문장 시작
- 문장 중간
- 문장 끝
- 여러 숫자·단위가 한 문장에 존재
- 같은 단위가 서로 다른 의미로 한 문장에 존재

예:

```text
손님 5분이 도착했고 회의는 5분 뒤 시작했다.
```

두 `5분`이 각각 다른 읽기로 처리되어야 한다.

## 18.2 대조 테스트

각 긍정 예에는 반드시 반대 의미 예를 둔다.

```text
3번 전화했다 / 3번 버스를 탔다
작품 3점을 전시했다 / 평점은 3점이다
자동차 3대를 샀다 / 가족 3대가 모였다
학생을 3조로 나눴다 / 예산은 3조 원이다
신문 3부를 인쇄했다 / 행사 3부가 시작됐다
건물 3동을 지었다 / 아파트 3동에 산다
```

## 18.3 유보 테스트

- 맨몸 `N단위`
- 앞 명사가 생략된 표현
- 뒤 동사가 다의적인 표현
- 후보 의미가 둘 이상인 표현
- 문장 밖 문맥이 필요한 표현
- 등록되지 않은 anchor
- 신조어·고유명사와 결합한 표현

## 18.4 비정상 숫자 테스트

```text
01분
+3번
-3점
3.5대
1,00조
3A번
```

새로운 고유어 수량 규칙이 이를 잘못 claim해서는 안 된다.

## 18.5 보호 구간 테스트

```text
[손님 5분]
`작품 3점`
/path/학생3조/file
{"value":"자동차 3대"}
H100_3번.json
```

현재 정책상 보호 대상인 표면 안에서는 새 규칙이 작동해서는 안 된다.

## 18.6 부분 변환 금지 테스트

다음과 같은 출력이 발생하지 않아야 한다.

```text
삼번 확인했다
3 번 확인했다
세3번
삼점이 공개됐다
```

# 21. 승인 기준

## 21.1 절대 기준

다음은 한 건이라도 발생하면 배포를 중단한다.

- 보호 구간 변경
- 코드·URL·파일명 변경
- 태그 또는 내부 정보 노출
- 숫자 값 변경
- 단위 변경
- 조사·어미 변경
- 부분 숫자 변환
- 같은 span의 중복 처리
- 유보 span의 generic fallback 재진입
- 기존 날짜·전화번호·통화 owner 회귀
- 패키지와 소스 실행 결과 불일치

## 21.2 확정 규칙 승인 기준

권장 기준:

- 수동 판정 corpus에서 매우 높은 정밀도
- 잘못된 확정 사례가 발견되면 규칙 범위를 즉시 축소
- 미처리보다 오처리를 더 심각하게 평가
- 자주 등장한다는 이유만으로 규칙을 확대하지 않음
- 새로운 anchor는 개별 승인

## 21.3 유보 규칙 승인 기준

유보 규칙은 다음을 만족해야 한다.

- 실제로 둘 이상의 읽기가 가능한 표면을 차단함
- 기존 확정 owner를 가로막지 않음
- 숫자·단위 전체를 원문으로 유지함
- generic fallback을 확실히 차단함
- 통합 LLM 호출 조건에 해당함
- LLM 실패 시 안전한 운영 경로가 있음

# 23. 규칙 승격 절차

유보된 표현을 향후 확정 규칙으로 옮길 때는 다음 절차를 따른다.

1. 실제 운영 corpus에서 반복 패턴을 수집한다.
2. 같은 표면의 모든 주요 반대 의미를 수집한다.
3. 의미를 확정하는 최소 anchor를 찾는다.
4. anchor가 없는 경우에는 승격하지 않는다.
5. 긍정·대조·보호·비정상 숫자 테스트를 만든다.
6. shadow에서 기존 결과 및 LLM 결과와 비교한다.
7. anchor별 정밀도를 검토한다.
8. 검증된 anchor만 allowlist에 추가한다.
9. 전체 명사 범주로 일반화하지 않는다.
10. 배포 후 단위별 오판을 계속 감시한다.

# 26. 완료 조건

이번 규칙 엔진 업데이트는 다음 조건을 모두 만족할 때 완료된 것으로 본다.

1. 기존 서비스 문자열 계약이 유지된다.
2. 서비스 출력에 태그나 내부 정보가 없다.
3. 확정·유보·절대 보존·비대상의 내부 구분이 가능하다.
4. 유보 span은 이후 owner에 재진입하지 않는다.
5. 새 규칙은 기존 숫자 renderer를 사용한다.
6. 새 문맥 규칙은 관리 사전과 분리된다.
7. Batch별 긍정·대조·유보·보호 테스트가 준비된다.
8. 소스와 배포 산출물의 probe 결과가 일치한다.
9. Prompt V1 연결 전에는 유보를 shadow로만 검증할 수 있다.
10. Prompt V1 연결 후에는 유보된 숫자 표면이 LLM 처리 대상으로 정확히 남는다.
11. 내부 후보 정보는 서비스 출력과 분리되어 있다.
12. 후속 3단계에서 후보 정보와 span 정보를 LLM 요청에 연결할 수 있다.

# 27. 최종 설계 요약

규칙 엔진 업데이트의 핵심 흐름은 다음과 같다.

```text
보호 표면인가
→ 보호

기존의 구체적인 owner가 확정할 수 있는가
→ 기존 방식으로 변환

새로운 좁은 문맥 규칙이 정확히 확정할 수 있는가
→ 기존 숫자 renderer로 변환

숫자+단위는 인식됐지만 의미가 둘 이상인가
→ 표면 전체를 원문으로 유지하고 처리 종료

어느 문맥형 단위에도 해당하지 않는가
→ 기존 generic 처리 진행
```

가장 중요한 원칙은 다음 두 문장으로 정리할 수 있다.

> 확정 규칙은 좁게 만들고, 유보 규칙은 generic 오판을 막을 만큼 충분히 앞에 둔다.

> 유보는 실패가 아니라 후속 LLM 처리를 위한 정상적이고 종료적인 판정 결과다.
